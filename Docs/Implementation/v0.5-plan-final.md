# v0.5 — Analysis and Presentation Implementation Plan

## Purpose

This document defines the implementation plan for **v0.5 — Analysis and Presentation**.

v0.4 established and validated the landing-detection and event evidence
framework. v0.5 begins the transition from development/validation harnesses to
user-facing analysis.

The first v0.5 deliverable is the **Event Timeline** Analyse-menu item.

The Event Timeline is deliberately first because it exercises the new
architecture without immediately adding interpretation or tuning
recommendations. It consumes the structured evidence already produced by the
v0.4 framework and presents it as a coherent, human-readable flight narrative.

The later v0.5 Landing Analysis deliverable builds on the same foundation.

---

# Architecture Reference

The current architecture is based on a common decoded `FlightLog` with
specialised processors providing different views of the same flight data.

These processors are intentionally parallel rather than forming one mandatory
linear processing chain.

Flight-window scope applies to time-series flight evidence and events.
Log-level parameters, configuration and other static context are not
flight-window bounded and may be used by analyses as contextual information.

```text
                     ┌─────────────────┐
                     │    BIN LOG      │
                     └────────┬────────┘
                              │
                              ▼
                     ┌─────────────────┐
                     │  log_reader.py  │
                     └────────┬────────┘
                              │
                              ▼
                     ┌─────────────────┐
                     │ flight_data.py  │
                     │   FlightLog     │
                     └────────┬────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
          ▼                   ▼                   ▼
 FlightWindowDetector   flight_segmenter   EventExtractor
          │                   │                   │
          ▼                   ▼                   ▼
   FlightWindow(s)      FlightSegment(s)    Event(s)
          │                   │                   │
          └───────────────────┼───────────────────┘
                              │
                     ┌────────┴────────┐
                     │                │
                     ▼                ▼
          LandingWindowDetector   other processors
                     │
                     ▼
              LandingWindow(s)
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
    Airspeed data         Sensor health
          │                     │
          └──────────┬──────────┘
                     ▼
              analyses/landing.py
                     │
                     ▼
              analyses/result.py
                     │
                     ▼
                  analyse.py
```

### Architectural Principles

- `log_reader.py` converts the raw ArduPilot log into the common
  `FlightLog` representation.
- `flight_data.py` provides the shared flight-data model.
- `FlightWindowDetector`, `flight_segmenter`, `EventExtractor`, and
  `LandingWindowDetector` are specialised evidence/data processors.
- These processors operate from the common flight data and are not intended
  to form a single mandatory processing chain.
- `FlightWindow` identifies the bounds of an actual flight.
- `FlightSegment` describes meaningful phases or portions of a flight.
- `Event` provides discrete logged events and state transitions.
- `LandingWindow` identifies a specific landing attempt within a flight.
- Additional processors such as airspeed and sensor-health analysis provide
  specialised measurements or evidence.
- Analysis modules combine these independent sources into an engineering
  result.
- `analyse.py` remains the application entry point and menu/presentation
  layer.

### Design Rule

**Processors should provide evidence; analysis modules should interpret and
combine that evidence.**

Avoid moving analysis-specific interpretation into low-level processors unless
there is a clear reason for it to be reusable by multiple analyses.

# v0.5 Phase 1 — Event Timeline

## Objective

Promote the validated event timeline from a development harness into the first
user-facing Analyse-menu deliverable.

The Event Timeline provides a chronological, flight-scoped view of important
events detected from the log.

It must consume the existing structured event/window data rather than
reimplementing event extraction or landing detection.

## Menu Integration

- [ ] Add **Event Timeline** to the Analyse menu.
- [ ] Make the menu action operate on the selected log/flight context.
- [ ] Present one timeline for the selected `FlightWindow`.
- [ ] Support selecting among multiple flights in a log.
- [ ] Keep the existing development harness available for regression
      validation.
- [ ] Do not make the development harness the production UI.

## Timeline Sources

The first implementation should expose the validated event sources already
established by v0.4:

- firmware `MSG`
- `LAND.stage`
- MODE transitions
- landing-window boundaries
- landing-attempt termination evidence

Optional evidence sources may be shown when available:

- rangefinder events
- airspeed-related events or measurements
- other validated sensor events

Optional sensors must not become prerequisites for displaying the timeline.

## Timeline Content

For each event, provide:

- timestamp
- event type
- human-readable description
- relevant value/state where applicable
- associated flight context
- associated landing attempt where applicable

Landing events retain the validated LAND semantics:

| Stage | Meaning |
|---:|---|
| 0 | NORMAL |
| 1 | APPROACH |
| 2 | PREFLARE |
| 3 | FINAL |

Raw landing fields may be exposed where useful:

- `stage`
- `fh`
- `slope`
- `slopeInit`
- `altO`

`fh` must continue to be labelled as **flare-timing height**.

## Landing Attempt Presentation

When a `LandingWindow` exists, the timeline should make the attempt boundaries
obvious.

Show:

- landing attempt start
- landing attempt end
- landing outcome where established
- termination reason where available
- LAND-stage progression
- relevant MSG events
- MODE transitions
- rangefinder evidence when present

The timeline must not imply that optional evidence was present when it was not.

## Time Presentation

- Internal calculations continue to use `TimeUS`.
- Human-readable timestamps use `MM:SS.mmm`.
- Event ordering must be deterministic.
- Events with identical timestamps must have a deterministic display order.

# v0.5 Phase 2 — Battery Analysis

## Objective

Add **Battery Analysis** to the Analyse menu as a simple, flight-scoped
analysis of logged electrical behaviour.

The initial implementation is deliberately measurement-based. It should use
the battery data already exposed by the BIN and add only simple, traceable
derived values.

**No battery chemistry is assumed.**

This makes the feature useful for both LiPo and Li-ion packs without embedding
chemistry-specific voltage thresholds into the analysis.

## Menu Integration

- [ ] Add **Battery Analysis** to the Analyse menu.
- [ ] Make the menu action operate on the selected `FlightWindow`.
- [ ] Support comparison of battery behaviour across flights.
- [ ] Keep battery analysis independent of landing detection.
- [ ] Use the existing battery telemetry in `FlightLog`.

## Primary Battery Measurements

Report:

- [ ] Start voltage
- [ ] Final voltage
- [ ] Minimum voltage
- [ ] Maximum current
- [ ] Average current
- [ ] Total mAh consumed
- [ ] Flight duration
- [ ] mAh/minute
- [ ] Maximum power
- [ ] Total energy in Wh

These are measurements or directly derived quantities. They should not be
turned into battery-health conclusions.

## Voltage Sag

Identify the highest-current event, or other clearly significant high-current
events if the data supports them.

For the selected event, report:

```text
Current                 xx.xx A
Voltage before          xx.xx V
Minimum voltage         xx.xx V
Voltage sag              x.xx V
```

The voltage baseline should be taken immediately before the significant load
event, with the minimum voltage measured during the event.

Where useful, also report:

- sag in volts
- sag per ampere as a derived indicator

Sag per ampere is an indicator only. It must not be presented as a definitive
measurement of battery internal resistance.

## Voltage Recovery

After a significant current event, measure voltage recovery after a defined
time interval.

Initial implementation:

```text
Recovery interval       5 seconds
Voltage before          xx.xx V
Minimum voltage         xx.xx V
Voltage after 5 s       xx.xx V
Voltage recovery         x.xx V
```

The recovery interval should be a named analysis setting so it can be made
configurable later if required.

Recovery is useful because it distinguishes transient load sag from the
underlying battery voltage.

If there is insufficient telemetry after the event to measure the complete
recovery interval, report the measurement as unavailable rather than
extrapolating it.

## Significant Load Event

The first implementation should focus on the highest-current event rather than
trying to classify every throttle or motor-load fluctuation.

- [ ] Identify the highest-current event.
- [ ] Record its timestamp.
- [ ] Capture voltage immediately before the event.
- [ ] Capture minimum voltage during the event.
- [ ] Calculate voltage sag.
- [ ] Capture voltage after 5 seconds where available.
- [ ] Calculate voltage recovery where available.

Future versions can examine multiple significant load events.

## Battery Report

Initial report structure:

```text
BATTERY ANALYSIS — Flight xx

Flight duration          xx:xx
Start voltage            xx.xx V
Final voltage             xx.xx V
Minimum voltage           xx.xx V

Maximum current           xx.xx A
Average current           xx.xx A
Maximum power             xxx W
Energy consumed           xxx Wh
Capacity consumed         xxxx mAh
Consumption rate          xxx mAh/min

HIGHEST-LOAD EVENT

Time                      xx:xx.xxx
Current                   xx.xx A
Voltage before            xx.xx V
Minimum voltage            xx.xx V
Voltage sag                x.xx V
Voltage after 5 s         xx.xx V
Voltage recovery           x.xx V
```

A voltage/current graph may be added later as a presentation enhancement,
using the existing development analysis as a reference. It is not required
for the initial Battery Analysis checkpoint.

## Battery Chemistry

The initial Battery Analysis does **not** attempt to determine chemistry.

- [ ] Do not hard-code LiPo voltage thresholds.
- [ ] Do not hard-code Li-ion voltage thresholds.
- [ ] Do not infer remaining capacity from voltage alone.
- [ ] Do not classify the battery as good/bad from voltage sag alone.
- [ ] Keep chemistry-specific interpretation deferred.

The measurement layer therefore remains valid when moving between LiPo and
Li-ion packs.

## Battery Analysis Acceptance Criteria

- [ ] Battery Analysis is accessible from the Analyse menu.
- [ ] It operates on a selected `FlightWindow`.
- [ ] Voltage and current are displayed where available.
- [ ] Average current is reported.
- [ ] Total mAh is reported where available.
- [ ] Energy in Wh is calculated where the required measurements exist.
- [ ] mAh/minute is reported where valid.
- [ ] Maximum power is reported where valid.
- [ ] Highest-current event is identified.
- [ ] Voltage sag is measured for the significant event.
- [ ] Voltage recovery after 5 seconds is measured where data permits.
- [ ] Missing data is explicitly reported.
- [ ] No chemistry-specific assumptions are made.
- [ ] No battery-health score is generated.
- [ ] No charging, low-voltage, or replacement recommendation is generated.
- [ ] Existing v0.4 regression behaviour remains unchanged.

# v0.5 Result Model

Analysis results remain separate from source telemetry.

```text
FlightLog
    └── source telemetry

AnalysisResult
    ├── analysis scopes
    └── analytical results
```

Metrics should contain, where applicable:

- measured value
- units
- source/evidence
- applicable time/window
- confidence or validity

Do not copy raw telemetry into the result model merely for convenience.

---

# v0.5 Evidence and Interpretation Rules

The v0.5 analysis layer must preserve the distinction between:

1. **Measurement**
2. **Evidence**
3. **Observation**
4. **Conclusion**

A conclusion must be supported by telemetry and documented ArduPilot source
behaviour.

Do not infer an aircraft state from an isolated value when the available
timeline or state evidence does not support it.

Optional sensor data remains optional evidence.

In particular:

- rangefinder availability must not determine whether a landing occurred;
- absence of rangefinder data must be explicitly tolerated;
- airspeed availability must not silently become a prerequisite for the
  landing window;
- ARM/DISARM must not be treated as a mandatory landing termination signal;
- firmware-specific semantics must remain behind the validated framework.

## Landing Foundation Audit — Complete

The Phase 3 landing-foundation audit is complete. Implementation confirmed that the existing evidence framework could supply most of the required landing evidence without introducing another parallel analysis layer.

### Implemented Foundation

The landing foundation now provides one bounded `LandingAttempt` analysis containing:

- landing-attempt temporal scope;
- authoritative landing-window termination reason;
- approach-start altitude;
- logged glide-slope angle;
- preflare time and flare-timing height;
- preflare airspeed where available;
- preflare GPS groundspeed;
- preflare sink rate derived from local barometric altitude;
- flare time and flare-timing height;
- flare sink rate;
- flare airspeed where available;
- flare GPS groundspeed;
- logged flare distance;
- optional rangefinder acquisition, continuity and dropout evidence;
- GPS landing/rollout completion evidence where GPS stop is the authoritative landing-window boundary;
- elapsed time from flare initiation to GPS stop.

`LandingAttemptProcessor` combines this evidence into `LandingAttemptAnalysis`. It remains descriptive: it does not classify a landing as good or bad and does not recommend parameter changes.

### Evidence Ownership

| Landing evidence | Source / owner | Foundation status |
|---|---|---|
| Attempt bounds | `LandingWindowDetector` / `LandingAttemptExtractor` | Implemented |
| Termination reason | `LandingWindow.end_reason` | Implemented |
| Approach altitude | firmware `MSG` via landing attempt processor | Implemented |
| Glide slope | firmware `MSG` / event evidence | Implemented |
| Preflare / flare stages | `LAND.stage` via `EventExtractor` | Implemented |
| Preflare sink rate | `BARO` local altitude rate | Implemented |
| Preflare / flare airspeed | `ARSP` / firmware flare message | Optional, implemented |
| Preflare / flare groundspeed | `GPS.Spd` | Implemented |
| Rangefinder acquisition / continuity | `RangefinderEvents` | Optional, implemented |
| Landing/rollout end | `GPSStopDetector` through `LandingWindowDetector` | Implemented |
| Sensor health | separate sensor-health report | Intentionally separate |
| Battery evidence | standalone Battery Analysis | Excluded from landing |

### GPS Landing / Rollout Completion

Sustained low GPS groundspeed has been extracted into the reusable `GPSStopDetector`. The configured landing rule remains the authoritative evidence used by `LandingWindowDetector`.

For a GPS-ended landing, `LandingWindow.end_us` is the beginning of the already-confirmed sustained low-speed interval. `LandingAttemptProcessor` consumes that proven boundary rather than attempting to re-detect GPS stop inside the already-truncated attempt.

The landing result records:

- `gps_stop_time_us`;
- configured GPS speed threshold;
- configured persistence duration;
- `flare_to_gps_stop_s`.

For wheeled landings represented by the regression data, this provides a robust end-of-landing/rollout boundary. It is deliberately named GPS stop rather than touchdown.

### Touchdown — Deferred

Exact touchdown detection remains intentionally undefined.

A dedicated evidence diagnostic compared GPS groundspeed, barometric altitude and optional rangefinder distance from immediately before flare through GPS stop on the completed wheeled landings. The evidence showed a repeatable landing-to-rollout sequence but did not establish a sufficiently robust rangefinder-independent touchdown timestamp.

Therefore:

- `TOUCHDOWN` remains reserved and unused;
- barometric altitude alone is not used as a touchdown detector;
- rangefinder evidence may support later touchdown work but remains optional;
- GPS stop is not relabelled as touchdown;
- flare-to-GPS-stop time includes both the remaining airborne flare phase and rollout and must not be labelled rollout duration.

A future detector may split the sequence into:

```text
flare -> touchdown -> GPS stop
          |             |
          |             +-- end of landing / rollout
          +---------------- actual ground contact
```

without changing the meaning of the existing GPS-stop fields.

### Optional Sensors

Airspeed and rangefinder remain optional evidence. Neither is required to detect or bound a landing attempt. GPS stop is also not the only possible termination source: abort, disarm, mode transition, or the parent flight-window end can terminate a landing window when applicable.

Sensor-health interpretation remains a separate report rather than being embedded in `LandingAttemptAnalysis`.

### Audit Outcome

The audit has moved from planning to implemented foundation. No additional generic landing evidence processor is currently required before building the presentation layer.

The next Phase 3 work is the user-facing Landing Analysis presentation/result integration using the existing `LandingAttemptAnalysis` evidence. Richer geometry, aircraft-response and exact-touchdown metrics remain later Phase 3/Checkpoint 4 work and should only be added when supported by defensible evidence.
