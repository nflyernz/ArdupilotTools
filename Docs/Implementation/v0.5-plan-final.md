# Purpose

v0.4 established and validated the landing-detection and event-evidence
framework.

v0.5 converts that framework into useful engineering analyses and
human-readable presentation.

The central rule remains:

> **Processors provide evidence; analysis modules combine and present
> that evidence.**

Analysis remains descriptive and evidence-based.

The analyzer reports what the log contains and what can be objectively
derived from it. It does not classify a landing as good or bad and does
not recommend parameter changes.

# Architecture Reference

The architecture uses a common decoded `FlightLog` with specialised
processors providing independent views of the same flight data.

These processors are intentionally parallel rather than forming one
mandatory processing chain.

``` text
                     ┌─────────────────┐
                     │    BIN LOG      │
                     └────────┬────────┘
                              │
                              ▼
                     ┌─────────────────┐
                     │  FlightReader   │
                     └────────┬────────┘
                              │
                              ▼
                     ┌─────────────────┐
                     │    FlightLog    │
                     └────────┬────────┘
                              │
          ┌───────────────────┼────────────────────┐
          │                   │                    │
          ▼                   ▼                    ▼
 FlightWindowDetector   FlightSegmenter      EventExtractor
          │                   │                    │
          ▼                   ▼                    ▼
   FlightWindow(s)      FlightSegment(s)         Event(s)
          │
          ▼
 LandingWindowDetector
          │
          ▼

          │
```

Other analyses operate alongside this structure rather than being forced

# Core Design Rules

## Evidence Before Interpretation

The analysis must preserve the distinction between:

1.  measured values;
2.  logged evidence;
3.  derived measurements;
4.  interpretation.

A derived value must have a defensible relationship to source telemetry.

The analyzer must not invent an aircraft state from an isolated value
when the available state or timeline evidence does not support it.

## Optional Sensors Remain Optional

-   Rangefinder availability must not determine whether a landing
    occurred.
-   Absence of rangefinder data must be tolerated.
-   Airspeed availability must not become a prerequisite for landing
    detection.
-   ARM/DISARM must not become a mandatory landing termination
    criterion.
-   Missing optional evidence should produce `Unavailable`, not a
    guessed value.

## No Landing Judgement

v0.5 does not produce:

-   landing-quality scores;
-   good/bad landing classifications;
-   tuning recommendations;
-   parameter-change recommendations;
-   speculative touchdown measurements.

Unusual measurements are reported without judgement.

# Landing / Rollout Completion

## GPS Stop

GPS groundspeed persistence provides the validated landing/rollout
completion boundary where available.

Current configured rule:

``` text
groundspeed <= 3.0 m/s
persisting for 2.0 s
```

The persistence detector owns this boundary.

`LandingAttemptProcessor` consumes the already established boundary
rather than independently recreating the stop detector.

Implemented measurements:

-   [x] GPS-stop time;
-   [x] flare-to-GPS-stop elapsed time;
-   [x] landing/rollout termination reason.

GPS stop means **landing/rollout completion**. It does not mean exact
touchdown.

# Final Landing Outcome Metric --- Distance from Target ✅

The final metric added before presentation cleanup is:

``` text
landing_end_target_distance_m
```

## Definition

For a GPS-ended landing, this is the horizontal distance between:

1.  the applicable `MAV_CMD_NAV_LAND` mission target; and
2.  the aircraft GPS position associated with the authoritative GPS-stop
    boundary.

## Interpretation Boundary

This value is **not touchdown accuracy**.

The aircraft may travel after touchdown before reaching the GPS-stop
boundary.

Therefore the metric represents:

> final landing/rollout position relative to the intended LAND target.

Likewise:

-   logged flare distance remains flare-time distance evidence;
-   flare-to-stop remains elapsed time from flare through the remaining
    airborne phase and rollout;
-   GPS stop remains the landing/rollout completion boundary;
-   exact touchdown remains deferred.

No along-track or cross-track error is currently required.

Radial horizontal distance is sufficient for the initial user-facing
analysis.

# Mission Target Provenance Hardening ✅

CMD records are treated as mission snapshots rather than independent
target updates.

The applicable LAND target is accepted only from a complete mission
snapshot.

A valid snapshot requires:

-   [x] one shared `CTot`;
-   [x] consecutive `CNum` values;
-   [x] exactly `CNum = 0 ... CTot - 1`;
-   [x] snapshot completion before the landing attempt begins;
-   [x] exactly one valid `MAV_CMD_NAV_LAND`;
-   [x] usable LAND coordinates.

The latest complete applicable snapshot is selected.

If the mission snapshot is incomplete, malformed, ambiguous, missing,
missing a LAND command, containing multiple LAND commands, or lacking
usable coordinates, target-dependent measurements are `Unavailable`.

The analyzer does not guess the target.

# Known and Intentional `Unavailable` Cases

`Unavailable` is a valid analysis result.

Examples include:

-   no final-flare event;
-   missing optional ARSP data;
-   missing optional RFND data;
-   no GPS-stop completion boundary;
-   incomplete CMD mission snapshot;
-   ambiguous mission snapshot;
-   missing applicable LAND target;
-   unusable LAND target coordinates;
-   inability to establish a requested measurement from the available
    evidence.

The analyzer should prefer `Unavailable` over inference.

# Development Rule After Community Review

Any proposed new landing metric should answer three questions before
implementation:

1.  **What engineering question does it answer?**
2.  **Which telemetry or documented ArduPilot behaviour supports it?**
3.  **Can it be measured without inventing an aircraft state?**

If those questions cannot be answered clearly, the metric should remain
deferred.
