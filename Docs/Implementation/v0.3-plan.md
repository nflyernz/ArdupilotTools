# v0.3 — Analysis Framework Implementation Plan

## Purpose

This document defines the implementation plan for:

**v0.3 — Analysis Framework**

The objective is to standardise processors, detectors, event processing, analysis orchestration, and shared utilities around the FlightWindow architecture completed in v0.2.

This is an implementation plan.

Architectural authority remains:

- `Docs/Architecture.md`

Milestone scope and status remain:

- `Docs/Roadmap.md`

Verified behaviour and regression evidence remain:

- `Docs/Validation.md`

---

# Architectural Baseline

v0.2 established the following architecture:

- `FlightReader` produces one `FlightLog`.
- `FlightLog` is the sole owner of decoded telemetry, parameters, events, mode segments, metadata, and detected flights.
- `FlightLog.flights` contains detected `FlightWindow` instances.
- `FlightWindow` is a lightweight `start_us` / `end_us` scope.
- `FlightWindow` does not own telemetry.
- Per-flight processors and detectors receive `FlightLog + FlightWindow`.
- Analysis-specific windows such as `SensorHealthWindow` and `LandingWindow` are child scopes of a `FlightWindow`.
- Child windows must remain within their parent `FlightWindow`.
- Firmware-specific parameter names and units are normalised by `ParameterReader`.
- Internal calculations use `TimeUS`.
- Analysis output must remain objective and reproducible.

The v0.3 refactor must preserve this architecture.

---

# Scope

v0.3 is an API and architecture consolidation milestone.

Primary work:

1. shared scope and filtering utilities;
2. detector contract consolidation;
3. sensor processor API consolidation;
4. event and rangefinder processing consolidation;
5. reusable per-flight analysis API;
6. development harness migration and final validation.

The purpose is to make existing components follow consistent flight-scoped contracts before real landing detection is implemented.

---

# Explicitly Deferred

The following work is **not part of v0.3**:

- real landing-attempt detection;
- authoritative `LAND.stage` semantics;
- multiple true landing attempts per flight;
- touchdown detection;
- flare detection;
- abort detection;
- restart detection;
- rollout detection;
- landing metrics;
- landing recommendations;
- landing reports;
- landing plots;
- HTML/PDF/JSON reporting;
- new sensor-health rules;
- changed airspeed validation criteria;
- changes to the validated FlightWindow boundaries;
- changes to the 2-second flight-start persistence algorithm;
- full automated regression framework.

These belong to v0.4 or later.

`LandingWindowDetector` must continue returning its current bounded development window during v0.3.

# Known Deviations

## Airspeed Processor

Current pattern:

```text
AirspeedProcessor(flight)

health(window)
analyse(window)
```

Problems:

- parent `FlightWindow` is not explicit;
- child-window containment is not centrally validated;
- telemetry filtering is duplicated;
- health and analysis paths duplicate result-building logic.

Target:

```text
AirspeedProcessor(
    flight_log,
    flight_window,
)
```

with explicit child scopes supplied to health or analysis methods.

---

## GPS and Barometer Processors

Current pattern:

```text
GPSProcessor(flight, window)
BarometerProcessor(flight, window)
```

Problems:

- argument names are ambiguous;
- parent flight scope is not clearly distinguished from an analysis-specific child scope;
- APIs differ from the intended common processor architecture.

Target:

```text
Processor(
    flight_log,
    flight_window,
)
```

with an optional child analysis window supplied to the processing method.

---

## Rangefinder Processing

Current rangefinder processing accepts a flight, one window, and configuration.

Problems:

- parent `FlightWindow` is not explicit;
- `LandingWindow` containment is not centrally validated;
- current callers provide `Config/landing.yaml`, while rangefinder settings are expected from sensor configuration;
- missing settings silently fall back to defaults.

Target:

```text
RangefinderEvents(
    flight_log,
    flight_window,
    landing_window,
    sensor_config,
)
```

---

## Arm Cycles

Current `ArmCycleFinder` reads ARM records across the complete log despite conceptually operating on a flight.

Target:

```text
ArmCycleFinder(
    flight_log,
    flight_window,
)
```

ARM processing must be constrained to the selected FlightWindow.

---

## Analysis API

Current landing workflow is primarily embedded in interactive `run()` orchestration.

Target:

```text
LandingAnalysis.analyse(
    flight_log,
    flight_window,
) -> AnalysisResult
```

`run()` remains responsible for:

- interactive input;
- log selection;
- loading;
- iterating flights;
- CLI presentation;
- framework-error handling.

`analyse()` becomes the reusable per-flight analysis entry point.

# Known Bugs / Defects

## Airspeed Native Rate

`AirspeedProcessor` currently calculates native sample rate but stores the `native_rate` function object rather than the calculated numeric value in its result.

This is a concrete implementation defect and should be corrected during the airspeed processor refactor.

The fix must not alter existing airspeed validation criteria.

---

## Obsolete Airspeed Harness API

`Scripts/test_airspeed.py` currently calls an obsolete processor contract, including a `.run()` API that the current `AirspeedProcessor` does not provide.

The harness must be migrated to the v0.3 processor API.

---

## Rangefinder Configuration

`RangefinderEvents` expects rangefinder settings from configuration.

Current callers provide:

```text
Config/landing.yaml
```

which does not contain the intended rangefinder configuration.

The code therefore silently uses defaults.

During v0.3, rangefinder processing should receive the correct sensor configuration source.

---

## AIRSPEED_STALL Configuration

`FlightWindowDetector` can use normalised:

```text
AIRSPEED_STALL
```

when calculating its effective flight speed threshold.

However, the current landing parameter configuration does not explicitly request this parameter.

Adding it may change FlightWindow boundaries.

Because the current four boundaries are validated regression data, this must **not** be silently included in the v0.3 refactor.

Any `AIRSPEED_STALL` configuration change must be treated as a separate explicitly approved and validated change.

---

# Design Decisions

## FlightLog.events Lifecycle

For v0.3, scoped event extraction remains **transient**.

`EventExtractor.extract(flight_log, flight_window)` returns the events required by the selected analysis.

Do not introduce a de-duplicated event cache or event persistence lifecycle until a concrete consumer requires it.

This does not change architectural ownership:

- events originate from `FlightLog`;
- `FlightWindow` does not own events;
- scoped extraction is a view/filtering operation.

---

## Arm-Cycle Boundary Policy

For v0.3, ARM processing uses **strict FlightWindow scoping**.

Only ARM transitions whose timestamps lie within the selected FlightWindow are included.

Do not synthesize an artificial partial arm cycle when the aircraft was already armed before the FlightWindow began.

If later landing analysis requires pre-flight arming context, explicit boundary semantics can be designed at that time.

---

## Detector Interface Policy

"Standard detector interface" does not mean every detector must have an identical function signature.

`FlightWindowDetector` is log-level because it creates FlightWindows.

Its natural contract remains conceptually:

```text
FlightLog
    ↓
FlightWindowDetector
    ↓
FlightWindow(s)
```

Per-flight detectors use:

```text
FlightLog
    +
FlightWindow
    ↓
Detector
    ↓
Child Scope / Result
```

Do not redesign `FlightWindowDetector` merely to make its signature resemble per-flight detectors.

Responsible for analysing exactly one selected FlightWindow.

```text
FlightLog
    │
    ├── FlightWindow
    │       │
    │       ├── SensorHealthWindow
    │       │
    │       └── LandingWindow
    │       │
    │       ├── Sensor processors
```

contract.

FlightWindow remains a lightweight scope and does not own telemetry.

FlightLog remains the owner of decoded telemetry, parameters, events, mode segments, metadata, and detected flights.
